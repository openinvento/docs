# Single Sign-On Security Notes

:::info
Single sign-on (OpenID Connect) is available from OpenInvento v1.5.0. It is not part of v1.4.1 and earlier.
:::

OpenInvento acts as an OpenID Connect relying party (RP): it sends the user to an identity provider (OP), receives an authorization code and turns it into a local session. This page lists every relying-party requirement we checked, how the code handles it and how that was verified.

The login is built on [mozilla-django-oidc](https://github.com/mozilla/mozilla-django-oidc) 5.0.2 with PyJWT. Our extensions live in `backend/account_auth/oidc.py` (`OIDCBackend`, `OIDCLoginView`, `OIDCCallbackView` and helper functions). The requirements come from:

- [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) (sections 2, 3.1, 5.3, 5.7 and the security considerations in section 16)
- [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html) (section 4.3)
- [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) OAuth 2.0
- [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636) PKCE
- [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725) JSON Web Token Best Current Practices
- [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207) Authorization Server Issuer Identification
- [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) OAuth 2.0 Security Best Current Practice

Requirements that only concern the identity provider are listed as "not applicable" so that it is clear they were looked at.

## How it was verified

**Unit tests.** `backend/account_auth/tests_oidc.py` (135 test methods; 182 tests in the whole backend, all passing) runs the full login flow against a fake provider that signs real RS256 tokens. Every covered check in the table below has at least one automated test, the conformance suite or the provider matrix as evidence, including the checks that live in mozilla-django-oidc or PyJWT, so a library upgrade that drops one of them shows up as a failing test. Three checks are only backed by code review, as their evidence column says: SE-02 (no automatic redirect after logout), S16-04 (the access token is neither stored nor logged) and BCP-2.4 (no password grant). `oidc.py` has full branch coverage. The evidence column lists test method names.

**OpenID Foundation conformance suite.** The RP was run against the [OpenID Foundation conformance suite](https://openid.net/certification/) with the plans `oidcc-client-basic-certification-test-plan` (14 modules) and `oidcc-client-config-certification-test-plan` (6 modules), static client, `client_secret_basic`:

| Result | Count | Modules |
|---|---|---|
| Passed | 17 | all modules except the ones below |
| Skipped | 2 | `idtoken-sig-none` (in both plans): OpenInvento rejects the unsigned ID token without calling UserInfo; the suite then marks the module skipped, because clients are not required to support `alg: none` |
| Failed | 1 | `discovery-jwks-uri-keys` (see below) |

The one failure is an artefact of the test harness, not a finding. The module checks that the RP fetches the keys from the discovered `jwks_uri` and verifies the ID token with them; that check passed. The module then marks itself finished, but OpenInvento continues the normal login and calls the UserInfo endpoint, which reaches the already finished module and produces "Illegal test state change: FINISHED -> RUNNING". Module names in the table are shown without the `oidcc-client-test-` prefix.

**Provider matrix.** Real logins in a browser behind TLS against Pocket ID 2.18.0, Keycloak 26.8.1, Dex v2.44.0 and Authentik 2026.8.5: first login creates the account without a local password, the second login reuses it. A separate capture recorded each provider's discovery document, authorization response, token response and claims. This showed, for example, that Pocket ID and Dex return `token_type` in lower case, that Pocket ID and Keycloak send the RFC 9207 `iss` parameter and Dex does not, that Pocket ID sends `aud` as a one-element list, and that Authentik signs with HS256 when no signing key is selected and always sends `email_verified: false` with its default email mapping.

The provider certificates in the matrix come from the private CA of the TLS proxy, so every login also exercises `OIDC_CA_BUNDLE`. Four extra runs check the TLS settings against Keycloak: without the CA the login ends on the failure page, with `OIDC_CA_BUNDLE` or `OIDC_SKIP_SSL_VERIFICATION` it reaches the provider, and with both set OIDC stays disabled.

**Container image test.** The production Docker image behind a TLS reverse proxy (`https://inventory.test`) against Pocket ID: three complete logins, PKCE S256, `redirect_uri` built from `APP_URL`, and two front-channel attacks:

- *Code injection:* an authorization code issued to the attacker is injected into the victim's login. Pocket ID refuses the token request because the PKCE verifier does not match, and the victim stays logged out.
- *Login CSRF:* a callback link from another browser session is opened by the victim. It is rejected because the state is not bound to the victim's session, so the victim is not logged in as the attacker.

It also checked the local login rules (password login refused for SSO users, allowed for the break-glass account).

## Known limitations

- **Cookies and proxy headers (RFC 9700, section 4.13).** `USE_X_FORWARDED_HOST` is on, `SECURE_PROXY_SSL_HEADER` is not set, and session and CSRF cookies are not marked `Secure`. This concerns the whole application, not only single sign-on, and is tracked in [issue #81](https://github.com/openinvento/openinvento/issues/81).
- **Access is checked at login only.** Disabling a user at the provider does not end an existing OpenInvento session; it only prevents the next login. Deactivating the account in OpenInvento ends its sessions immediately.
- **No RP-initiated logout.** Logging out ends the OpenInvento session only. The provider session stays active, so the next "Sign in with ..." click may log in without a prompt. Automatic redirect to the provider is skipped right after a logout.
- **Parallel callbacks with the same state.** The state is deleted from the session before the token request, but not atomically. If the browser submits the same authorization request twice (double click, reload at the provider), the provider may issue two codes for the same state. Two callbacks that arrive at the same time in the same session can then both pass the state check, and each can redeem its own code. Both codes belong to the same authorization request (same nonce, same PKCE verifier), so the result is the same user logged in twice in their own session. Nobody else can use this: a callback in someone else's session needs that session's cookie, and a replayed code is refused by the provider (RFC 6749 4.1.2).
- **One provider.** Exactly one issuer can be configured. Mix-up attacks between several providers therefore do not apply; the `iss` response parameter is still checked.
- **Signing algorithms.** ID tokens must be signed with RS256/384/512 or ES256/384/512. HS256/384/512 are not supported on purpose: with HMAC the client secret is the signing key (Core 10.1), so anyone who can read it from the configuration, a backup or the provider could issue ID tokens for any user, and a public client has no secret at all. Every OpenID provider must support RS256 (Core 15.1). PS256/384/512 and EdDSA are not supported either. With any other value OIDC stays disabled and an error is logged at startup.
- **Client authentication.** `client_secret_post` (default), `client_secret_basic` (`OIDC_TOKEN_USE_BASIC_AUTH`) or none (public client with PKCE). `private_key_jwt` and mutual TLS are not supported.
